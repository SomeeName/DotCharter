# AI tone match — the MODEL lane (rig estimator)

The trained half of "match a tone from audio": wet guitar audio in, a guessed
effect chain with knob values out. It is a **prior for the search-based
matcher**, never a replacement — the ancestor literature's decisive finding
(Okita & Katayose 2026) is that DNN type prediction *plus* search over the real
renderer beats prediction alone on every metric, so a confident estimate that
the matcher then refines is the whole point of this lane.

Contract: `IRigEstimator` / `RigEstimate` in
`DotCharter.Services/Ai/Match/MatchContracts.cs`.

| Piece | Where |

## Two heads, and v1 stays the control

`tools/rig-model/train.py --head v1|v2`, **default `v1`**.

- **v1** — four independent heads; the chain is seven per-slot softmaxes.
- **v2** — the same front-end and family head, with the slot head replaced by a
  3-layer, d=256 autoregressive transformer decoder (5.22 M params) that emits
  `<bos> m1 … <eos>` and cross-attends the audio embedding. Per-emitted-module
  knob regression, confidence = `exp(mean log p)`, greedy in the graph, beam
  k=3 python-side only.

v1 is kept runnable and unchanged BECAUSE it is the control: what v2 has to beat
is the number v1 posts on the same data with the same metric code, and a change
that also moves its own baseline measures nothing. v1's cap is structural — slot
3 cannot see what slot 2 took — and it shows: family F1 **0.84** against
occupied-slot accuracy **0.42** on the first full-set CLAP run.

Design, conventions and the three invariants that hold the token space together
are in `tools/rig-model/README.md` § "Heads and loss"; the code is
`tools/rig-model/model_v2.py`, and its unit tests (decoder shapes, causality,
teacher-forcing vs greedy, beam ≥ greedy, the knob weighting, the readiness
metric, the ONNX round-trip) are `tools/rig-model/tests/test_v2.py` — which runs
**with or without pytest**, because the owner's venv has neither pytest nor a
reason to grow one.

## The v2 ONNX contract is ADDITIVE, and `SchemaVersion` does NOT move

A v2 export emits v1's four outputs — `family_presence`, `slot_probs`,
`knob_values`, `confidence` — with their v1 names, shapes and meaning, FILLED
FROM THE DECODER's greedy chain, plus two new ones (`chain_tokens`,
`chain_knobs`).

That is possible because **token `k + 2` IS slot class `k`** and **`EOS` IS the
`<none>` class**, so the decoder's own per-step distribution goes straight into
`slot_probs` and its argmax IS the decoded chain (asserted, not merely claimed:
`test_slot_probs_agree_with_the_decoded_chain`). **`SchemaVersion` stays at 1.**

**But "additive" was NOT free, and the way it failed is worth keeping.**
`EstimateAsync` used to materialise EVERY result of the ONNX run into
`float[]` — `results.ToDictionary(r => r.Name, r => r.AsTensor<float>()…)`. A
model publishing a fifth output it has no opinion about therefore THREW, and
the first cut of `chain_tokens` was `int64`, so the "additive" export would
have been unloadable by the shipped reader. And the shape of that failure is
the bad one: the app loads, `IsAvailable` is true, the first estimate throws
inside the session, the load failure LATCHES, and every caller degrades to
search-only for the rest of the process with one log line.

Both halves are fixed and both must stay:

- `RigEstimatorOnnx.EstimateAsync` reads **only the four outputs it needs, by
  name** (`ReadOutput`), and says which output is missing if one is. It is no
  longer coupled to the exporter's output list.
- the exporter publishes `chain_tokens` as **float32, not int64** — ids top out
  at 102 and are exact in fp32 — so even a reader that does map everything
  survives.

`RigEstimatorContractTests` pins the reader half against a committed ~23 KB
fixture ONNX that carries the v2 output signature with constant answers
(generated by `tools/rig-model/tests/make_contract_fixture.py`; its sidecar is
written from the LIVE `RigLabelVocabulary` at test time, so a catalogue change
moves the fixture's label space instead of leaving a stale copy that passes
while meaning something else). A real v2 export is tens of MB and is not
bundled, so a test against one could only ever skip.

**The rule, for whoever comes next:** bump `SchemaVersion` only when an EXISTING
output changes meaning, shape or index — not when one is added. A bump makes
every already-exported model unloadable, and here it would have bought nothing.
A future C# reader that wants the sequence directly finds the token convention
in the sidecar's `export.chain` block.

## The knob loss is weighted by MEASURED audibility

`tools/rig-model/knob_sensitivity.json` carries one number per (module, param):
the `ToneSimilarity` distance between two real JUCE offline renders of one fixed
DI through that module, the param at normalised 0.1 and at 0.9. Measured by
`tools/rig-dataset`'s `knob-sensitivity` subcommand — 573 params in 6 m 36 s,
deterministic. `tools/rig-model/sensitivity.py` turns it into the weight vector
and `model_v2.multitask_loss_v2` applies it.

Four things about it a reader must not have to rediscover:

- **Normalisation is per CONTEXT and by the 95th percentile.** 86 modules were
  measured solo and 12 behind a default `amp → cab` (the sweep probes which);
  those are not the same distance scale. The percentile rather than the max,
  because one very loud module would otherwise push everything else to the floor.
- **The 0.1 floor is load-bearing.** "The A/B did not move the distance" is not
  "this param does nothing", and a zero weight is an untrainable knob for ever.
- **Level knobs measure ~0 legitimately.** `RigRenderer` level-matches and the
  metric is content-invariant, so `master` / `makeupDb` / `outputDb` genuinely
  do not move it. That is the metric's position — arguably the right signal for
  a loss trained against that same metric, but a POSITION, not a fact about the
  ear.
- **`freeze`, `looper` and `namamp` measured all-zero because the A/B cannot
  reach them** (a footswitch, a trigger, a capture path). That is a gap in the
  MEASUREMENT, so `sensitivity.py` gives their params the MEDIAN weight, not the
  floor. Re-measure them properly before trusting a knob number from any of the
  three.

With no file present every weight is 1.0 and the term is v1's masked MAE
exactly, which is what keeps the two heads' knob numbers comparable.

## The readiness rate is the goal, in numbers

> "I want it to get to a point where you can skip the refinement and are ready
> to go most of the time."

`tools/rig-model/metrics.py`: a clip is **ready** when the chain is EXACTLY
right AND every knob of every module in it is within **0.1** of travel
(`ready_rate`), with a looser 0.2 beside it (`ready_rate_loose`). All-or-nothing
per clip on purpose — a rig with one knob 0.4 out is a rig the user has to go
and fix, and an average MAE hides exactly that. `chain_edit_distance` is
reported too, because exact match is brutal and slot accuracy is too kind: one
inserted pedal scores 0 on the first and near 0 on the second, and 1 on the edit
distance, which is what a user would say.

Both heads' numbers come from ONE piece of code on v1-shaped arrays. **The
metrics are always taken from a FREE-RUNNING decode**, never the teacher-forced
one — a teacher-forced accuracy is a different and much kinder number, and
reporting it is how a decoder looks fixed while its chains are still wrong.

`tools/rig-model/runs/pipeline-v2.ps1` runs the v2 stage unattended after
`pipeline-full` and **exports only if v2 beats v1 on `ready_rate`** — not on the
composite `pipeline-full` ships on. The two can disagree: the composite rewards
partial credit on every head, readiness does not. It refuses to export at all
when there is no comparable v1 number, rather than treating a missing field as
zero.

## The label space is generated, not written

`RigLabelVocabulary` is built from `DcRigTargetCatalog`, and
`RigLabelVocabularyTests` exports it to `tools/rig-model/rig_label_vocab.json`.
**That JSON is a build product — never hand-edit it**; running the gate
refreshes it. The trainer reads it, so a catalogue range that moves reaches
python without anyone re-typing a number.

Shape as of 2026-09-12: **100 modules**, **13 families**, a **573-dim** flat
knob vector, **7** chain slots, 5 s at 48 kHz.

**Thirteen families, not nine.** The nine `src/dsp/gear/*.cpp` files are source
files; the category vocabulary is the fixed set in `GearEntry.h`, and `cab`,
`eq`, `routing` and `synth` have no gear file of their own. The per-module
category is a hand-mirror of the native catalogue table (the managed
`DcRigTargetCatalog` mirrors ranges but not categories);
`EveryCatalogueModule_HasANativeCategory` fails if a module lacks a row rather
than letting `BuildModules`' `"utility"` fallback mislabel it in every training
row.

## Normalisation is a two-sided contract

A knob is normalised `(v - min) / (max - min)`, clamped, with a **non-finite
value reading as the catalogue DEFAULT** — a NaN passes every `<` and `>`, so an
unguarded clamp carries it into the training tensor and poisons the batch.
`RigLabelVocabulary.Normalise` and `vocab.py`'s `normalise` are line-for-line
twins; change one and change the other.

Input preparation is the same kind of contract: mono at 48 kHz, the **centre**
5 s, normalised to **−18 dBFS RMS** (the level the dataset renderer produces),
gain capped at 64×, digital silence left alone, non-finite samples scrubbed.
`RigEstimatorOnnx.PrepareInput` ↔ `export_onnx.py`'s `prepare_input`.

## Why the parity test exists, and what it must keep doing

**Drift between the two halves is silent.** A C# side that windowed differently,
normalised differently, or read the knob vector at the wrong offsets still
returns a well-formed `DcRigPreset` full of plausible numbers, and nothing
downstream can tell — a guess has no correct answer to compare against.

So `export_onnx.py` records a fixture clip's exact outputs in the sidecar and
`RigEstimatorParityTests` runs the **shipped ONNX** on a fixture it regenerates
itself. Two separate assertions, deliberately: the fixture's **sha256** (is the
input the same?) and the **outputs** (is the model the same?) — which separates
a normalisation bug from a model bug.

The fixture is **closed form** for exactly this reason. It had numpy Gaussian
noise in it first, which no C# test can reproduce; that would have forced it to
ship as a binary blob, and a blob goes stale against the formula without anyone
noticing.

Proven non-vacuous 2026-09-12 by moving `TargetRmsDbfs` from −18 to −17 dB:

```
The C# parity fixture is not the python one.
  expected sha256 23a11a86523562be493879fc07102968c6b7d02dfa3db53fd74f54002eaf30c4
  actual   sha256 27b771c3b2be840aa50a319e5243db1a9ab12132353992905139cc8a5be952fd
family 'drive' (index 3): python wrote 0.176330, C# produced 0.186395 (tolerance 0.002).
```

## Getting the model

**This lane shipped with no way for a real user to obtain its model at all.**
Nothing outside `RigEstimatorOnnx` and the python tools named
`ai-match\rig-estimator`, so `IsAvailable` was permanently false, the matcher
silently stayed search-only, and the only way to populate the folder was to run
`export_onnx.py` by hand. The table above used to imply exactly that. It is a
download now, by the same convention as the lyric acoustic models
(`Audio/Lyrics/LyricModelCatalog` / `LyricModelInstaller`).

| Piece | What it does |
|---|---|
| `RigEstimatorModelCatalog` | TWO entries since 2026-09-14: `rig-estimator` → `rig-estimator-v1.zip` (the model) and `rig-library` → `rig-library-v1.zip` (the pre-rendered retrieval library for the bundled DI; see [ai-match-search.md](ai-match-search.md) § "The library GROWS"). **Versioned in the asset NAME, not by a pinned tag** — the fetcher scans releases for the name, so re-uploading unchanged weights on every app release stays optional. |
| `RigEstimatorModelInstaller` | `.incoming` staging + atomic `Directory.Move`, never-overwrite, zip-slip and byte/entry caps through `BoundedZipExtractor`, non-throwing failure carrying a REASON string. |
| `RigEstimatorModelDownloadService` | `IRigEstimatorModelDownloadService`: is it installed, how big is the download, what does the installed sidecar say, fetch it. |
| the fetcher | **`LyricModelAssetFetcher`, reused and not forked.** It is a GitHub release-asset reader with nothing lyric-specific in it, and it carries the one piece of hard-won knowledge a copy would silently lose: the release scan must PAGE (5 × 100), because a model asset sits on a release a hundred behind HEAD. A fork would have re-broken the download the same way and reported it as "the model is not available". |

Rules that bite:

- **The MODEL's required files are `model.onnx` + `model.sidecar.json`
  (`RigEstimatorModelInstaller.ModelFiles`); `model.onnx.data` is OPTIONAL.** An
  export past the 2 GB protobuf limit writes its weights into that sibling blob;
  requiring it would refuse every self-contained export, and dropping it would
  leave the graph's external references dangling. **Since 2026-09-14 the
  required set is the ENTRY's** (`RigEstimatorModelDownload.RequiredFiles`,
  null ⇒ the model's), which is what lets the library entry name its one
  `.bin`: `IsInstalled(id, files)` and the payload-root search both take the
  list, and `RigEstimatorModelInstallerTests.TheLibraryEntryInstallsItsOwnFile_AndIsNotAModel`
  pins that a library folder never reads as an installed MODEL.
- **The library entry's file name is derived, and its DI fingerprint is a pinned
  CONSTANT.** `RigEstimatorModelCatalog.LibraryFileName` is
  `RigLibrary.CacheFileName(tonefx-v2, 4000, 20260912, LibraryDiFingerprint)` =
  `library-tonefx-v2-4000-20260912-5e4b70d7.bin` — the matcher's own cache name
  for the shipping key, so "is the installed library the one this DI needs" is
  the header check and not a convention. The fingerprint is a constant so the
  catalogue does not generate twenty seconds of audio to name a file;
  `RigLibraryCatalogTests.TheFingerprintIsTheOneTheAppComputesForTheBundledDi`
  recomputes it from `ReferenceDi.Medley()`. A changed medley fails that test,
  moves the constant, and means a `-v2` asset. **Its SHA-256 was filled on
  2026-09-14** (`rig-library-v1.zip`, 6,026,235 bytes, digest `f5663a676598…`),
  pinned by `RigLibraryCatalogTests.TheLibraryHashIsPublished_AndIsTheShippedArchivesDigest`;
  a re-cut asset changes that line in the same commit, never the installer's
  check.
- **The estimator is handed the INSTALLER's directory** (`App.MatchServices.cs`),
  not its own default. They are equal — `RigEstimatorModelCatalogTests` and
  `RigEstimatorModelInstallerTests` both assert it — and wiring it this way is
  what stops "where it is written" and "where it is read" becoming two paths.
- **The root is `LocalApplicationData`.** The lyric installer's roots are
  `%APPDATA%`; a reused installer that kept them would put 200 MB into a roaming
  profile, in a folder nothing reads.
- **The SHA-256 is not published yet, and the code says so rather than
  pretending.** `RigEstimatorModelCatalog.Download.Sha256` is empty because the
  v1 export does not exist; an empty hash degrades to a SIZE check (at least
  1 MB, within 4× of the estimate) and logs a WARNING on every install.
  **Filling it in is a one-line change** to that record — nothing else moves,
  the installer already enforces a published hash. **Filled on 2026-09-14**
  (`rig-estimator-v1.zip` = `rig-estimator-v2-r8-20260914`, 130,799,294 bytes),
  and `RigEstimatorModelCatalogTests.TheHashIsPublished_AndIsTheShippedArchivesDigest`
  pins the digest and size: a re-cut asset changes that line in the same
  commit, never the installer's check. A placeholder like `"TBD"` is
  REFUSED as a published hash (`HasPublishedHash` is shape-checked), because it
  would read as "integrity is enforced" while failing every real archive.
- **Two surfaces show the state and both must stay.** Settings ▸ AI ▸ Match
  model reports not-installed / installed (modelId, epoch, size) / installed but
  UNLOADABLE, with download + cancel + open-folder; the tone panel's "Match from
  audio" block carries a one-click offer beside its status line, mirroring how
  lyric auto-sync offers its own model. **"Installed" and "loads" are different
  questions** — a sidecar from another label space is installed and unusable —
  and the settings block asks both, the second only when the files are there.

## Runtime rules

- **CPU provider, 2 intra-op threads, through the stem path's own
  `OnnxSessionFactory`.** This runs while the audio engine is live; a tone guess
  is not worth a dropout, and a GPU session would contend with the separator's.
  Measured 150 ms per 5 s clip.
- **Nothing is bundled.** `IsAvailable` is false with no model and never throws,
  so every caller degrades to search-only. A load failure latches and is logged.
- **The sidecar's `schemaVersion` is checked on load.** A model exported against
  a different sidecar SCHEMA is refused rather than read.
- **A shipped model never needs a retrain when the catalogue grows.** Decode reads
  the knob vector through the MODEL'S OWN sidecar (its offsets, its ranges), then
  `RigEstimatorOnnx.ConformToCatalogue` re-expresses each module in today's
  catalogue BY NAME: a param the model does not predict takes its catalogue
  default, a predicted one is clamped to today's range, a param or module the
  catalogue dropped is dropped. Never decode a shipped model through
  `RigLabelVocabulary.Snapshot()`: the published `rig-estimator-v1.zip` is 573
  knobs and today's label space is 582 (#70 / #72), so every offset after `amp`
  would be wrong. Pinned by `RigEstimatorV1CompatibilityTests` against the v1
  label space in `DotCharter.Tests/Ai/Model/Assets/rig-estimator-v1-label-space.json`
  (that zip's sidecar minus its `export` / `parity` blocks).
- **Decode drops `routing` modules** — v1 is series-only, and a per-slot argmax
  cannot guarantee a splitter gets its merger. Same rule as `ToneDraftValidator`.

## Training on Windows: the Dataset must be cheap to PICKLE

Windows has no `fork`, so every `--workers N` DataLoader process is a fresh
interpreter and torch **pickles the whole `Dataset` down a pipe into each one**.
The first full-set run (49,908 clips) died on that, *after* its 25-minute cache
build:

```
multiprocessing/reduction.py dump -> OSError: [Errno 22] Invalid argument   (parent)
_pickle.UnpicklingError: pickle data was truncated                          (child)
```

`RigClips` held the fp16 PCM cache on the instance as an `np.memmap` — an
`ndarray` **subclass**, so pickling it serialises the whole 19.4 GB backing
store, not the filename — beside 40,413 rows of expanded labels (573 knobs +
573 mask floats each).

The rule, now data.py's docstring rule 4 and enforced twice: **the dataset
carries paths, shapes and the vocab and nothing else** (~38 KB pickled). The PCM
memmap, the four label `.npy` arrays and the clip-path list live in the cache
dir and are opened lazily in whichever process first asks; `__getstate__` drops
the handles. Never put an array, a memmap, an open file or a per-row list back
on `self` — it reads fine on Linux, where `fork` shares it, and is fatal here.
**`--workers 0` is not the fix**; it hides a design fault behind a slower loader.

- `python data.py --data <dir> --cache-dir <dir>` is the standalone guard.
- `train.py` re-asserts it **before it builds a single loader**, so a regression
  costs seconds instead of the cache build.

Two consequences worth knowing:

- **The label cache is a second on-disk artefact** (`<split>.{families,slots,
  knobs,knob_mask}.npy` + `<split>.paths.txt` + `<split>.labels.json`), ~145 MB
  for the full set, ~15 s to build. Its meta carries a **fingerprint of the
  split's clip paths in order**, because the cache is indexed positionally — a
  reordered or regrown manifest invalidates it at an unchanged row count. The
  fp16 PCM format and its `.meta.json` are unchanged, so an existing 19.4 GB
  cache is adopted rather than re-rendered.
- **Augmentation draws from a per-worker `np.random.Generator`** seeded from
  `torch.initial_seed()`. The process-global `np.random` is duplicated into
  every spawned worker, which would have handed all four the same gain and
  polarity stream — silent, and no assertion here would have caught it.

## Running the full comparison unattended

`tools/rig-model/runs/pipeline-full.ps1` is the one script: two self-tests → CNN
control (≤60 ep / 90 min cap) → eval → CLAP (≤45 ep / 240 min cap) → eval →
**one** export of whichever won. Below-normal priority, 4 workers,
`--require-gpu 3080` on every stage — `eval.py`'s default is `3080` now too,
because torch's `cuda:0` is the 5070 Ti the owner games on and an eval is still
a whole GPU. `runs/pipeline-full.log` plus one live log per stage;
`runs/STOP` halts it between stages.

**The LR horizon follows the TIME cap, not `--epochs`.** A one-cycle sized from
`--epochs 60` and then killed by `--minutes 90` stops around the LR *peak* —
measured here, `2.0e-4` of a `3.0e-4` max, against `3.0e-8` on a horizon that
fits — so the model never anneals and the GPU night is wasted. `--epochs` is a
**ceiling** now: epoch 1 warms up, `train.plan_epochs()` re-plans the horizon
from that epoch's own wall time
(`min(epochs, completed + time_left // (sec_per_epoch × 1.03))`, shrink-only
afterwards, because a horizon that grows pushes the cosine's end away for ever),
and the cosine lands on the last epoch that fits. Best-by-val checkpointing is
unchanged; `run.json` records `schedule.*`. `train.py --self-test-schedule`
gates the arithmetic with no GPU and no dataset, and is the pipeline's stage 0b
— it is what decides how good the shipped checkpoint is, and a training log
shows none of it.

The winner is chosen by a composite the script states in the open —
`0.4·family_micro_f1 + 0.4·slot_accuracy_occupied + 0.2·(1 − min(knob_mae/0.25, 1))`.
Types outweigh knobs deliberately: search refines a knob, it cannot invent a
module the estimator never proposed.

**Both front-ends share one `--cache-dir`.** 19.4 GB and ~25 min of render is
not worth paying twice for byte-identical audio; `train.py` records the dir in
`run.json` and `eval.py` reads it back, so an eval cannot silently re-render the
cache into its own run folder.

## Exporting

Everything in the graph is a **fixed-length linear transform on purpose**:
`torch.stft` has no opset-17 export ("STFT does not currently support complex
types") and `torch.fft.rfft` has none at all, so the mel is two `conv1d`s
against precomputed cos/sin kernels and the modulation branch is a matmul
against a 96-row DFT matrix. That is what keeps the mel *inside* the graph,
which is what stops C# needing a second mel implementation.

**Do not "fix" the export by switching to the dynamo exporter.** It was tried:
it printed a success line and wrote a 0.2 MB file (the opset downgrade had
failed with "No Adapter To Version 17 for Pad") whose every output was NaN. The
torch-vs-ORT check missed it because it read `if delta > 2e-3`, and a NaN fails
every comparison — it is `if not (delta <= 2e-3)` now.

## Current state

The data lane's renders had not landed, so the only trained checkpoints are on a
**crude synthetic smoke set** (`make_smoke.py`: gain, `tanh`, one-pole low-pass,
feedback delay). Those numbers prove the pipeline and nothing else, and its
**knob labels carry no signal by construction** — the toy renderer runs on its
own hidden parameters, not on the catalogue params in the label.

Front-end chosen by measurement: **CLAP HTSAT** (`laion/clap-htsat-unfused`,
MIT, 27.5 M, 77 ms CPU, 48 kHz native) over AST (Apache-2.0, 86.2 M, 1423 ms —
fails the in-app budget). On the crude set the **CNN control beat it**, which is
expected for a toy renderer and is precisely why the control exists: re-run both
on real renders before concluding anything.
